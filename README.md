# Wronki-News-Bot

Бот, який сам збирає новини Вронок та околиці (30 км) з 38 джерел і публікує їх
у Telegram-канал **«Новини Вронки та околиці»** (`-1004353266588`).

Працює на GitHub Actions — тобто **на вашому комп'ютері нічого не має бути
увімкнено**. Ви вимикаєте ноутбук — бот публікує далі.

- Репозиторій: https://github.com/enterpriseimpossible-sudo/wronki-news-bot
- Мова коду: Python 3.12 (у CI) / 3.13 (локально)
- Вартість: 0 (публічний репозиторій, GitHub Actions безкоштовні)

> **Найважливіше (26.10.2026).** Бот «тихо» зупинився 20.10.2026 і ніхто не помітив
> 87 годин: inline `curl` без `--fail` проковтнув помилку токена.
>
> - **Виправлено локально (у цій папці, НЕ в GitHub):** `wronki.yml` ставить наступний
>   прогін лише через `scripts/dispatch_next.sh` (падає червоним на всьому, крім HTTP 204),
>   має страховий `schedule` кожні 10 хв і `timeout-minutes`; доданий сторож
>   `wronki-watchdog.yml`; `monitor.py` ловить «прогін зелений, а ланцюжок обірвано».
>   Тести: 93 passed, 0 skipped.
> - **Потрібен власник:** запушити зміни токеном зі scope `workflow` (розділ 12),
>   запустити **Wronki watchdog** вручну, підтвердити канал. До пушу в GitHub працює
>   старий `wronki.yml` — без `--fail` і без страховки.

## 1. Що робить бот

1. Читає `config.json`: центр (Wronki), радіус (30 км), ліміт новин за прогін (5),
   «свіжість» (1 год), переклад PL→UA (увімкнено), список джерел.
2. Бере **38 увімкнених джерел**: RSS (8), HTML-сторінки (29), Telegram (1).
3. Відкидає все, що далі 30 км і старше за `max_age_hours`.
4. Перевіряє `state.json` — чи це вже публікували (за URL і за нормалізованим заголовком).
5. Публікує в канал: заголовок, короткий опис, фото, дату, посилання, гештеги.

## 2. Як це працює (схема)

```
GitHub Actions
│
└─ wronki.yml  ──► bot.py ──► Telegram-канал
     тригери:
       • workflow_dispatch — ручний запуск (вкладка Actions або панель)
       • самоланцюжок — кожен прогін ставить наступний через ~1 хв

     • schedule (*/10) — страховка: піднімає бота й ланцюжок, якщо той помер

   wronki-watchdog.yml (кожні 30 хв) ──► monitor.py ──► червоний job / алерт,
                                     └─► dispatch_next.sh --force, якщо ланцюжок мертвий
   monitor.py (локально) — те саме вручну
```

> `schedule` і `wronki-watchdog.yml` поки є **лише локально** — див. розділ 12.

**Чому самоланцюжок.** Він дає затримку ~2 хв замість 5–15 хв, але тримається
на одному токені: 20.10.2026 токен перестав працювати, `curl` без `--fail`
проковтнув помилку, прогін лишився зеленим, і ланцюжок обірвався назавжди.
Тепер (локально) крок ланцюжка — `bash scripts/dispatch_next.sh`: `--fail-with-body`,
3 спроби, успіх лише на HTTP 204, інакше червоний крок з кодом і текстом помилки
GitHub. Якщо ланцюжок усе ж помре, його піднімуть `schedule` і сторож.

## 3. Швидкий старт «з нуля» (10 хв)

### 3.1 Що знадобиться

- акаунт GitHub із правом писати в репозиторій;
- Telegram-канал, де ви адміністратор;
- 10 хвилин.

### 3.2 Токен бота

1. У Telegram відкрийте **@BotFather** → `/newbot` (або `/token`, якщо бот уже є).
2. Скопіюйте токен вигляду `123456789:AA...` — це `TELEGRAM_BOT_TOKEN`.
3. Додайте бота **адміністратором каналу** з правом «Публікувати повідомлення».
   Без цього Telegram поверне `403 Forbidden: bot is not a member of the channel`.

### 3.3 ID каналу

Для каналу це від'ємне число, наприклад `-1004353266588`. Найпростіше взяти з
посилання на пост: `https://t.me/c/4353266588/378` → ID `-1004353266588`
(додайте `-100` до числа після `/c/`).

### 3.4 Секрети в GitHub

**Settings → Secrets and variables → Actions → New repository secret:**

| Секрет | Обов'язковий | Що це |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | так | токен від @BotFather |
| `TELEGRAM_CHANNEL_ID` | так | ID каналу, напр. `-1004353266588` |
| `GH_PAT` | так (для самоланцюжка) | fine-grained PAT, див. нижче |
| `WRONKI_ALERT_CHAT_ID` | ні | ваш особистий chat_id для алертів — **не канал** |

**`GH_PAT`** (GitHub → Settings → Developer settings → Personal access tokens →
Fine-grained tokens):

- Repository access: **тільки** `wronki-news-bot`;
- Permissions → **Actions: Read and write**;
- Expiration: максимум 1 рік; поставте нагадку в календар за тиждень до кінця.

`GITHUB_TOKEN` для самоланцюжка **не підходить**: події, створені цим токеном,
не запускають нові workflow (захист GitHub від рекурсії). Саме тому потрібен PAT.

### 3.5 Перший запуск без публікації

Actions → **Wronki news bot** → **Run workflow** → поставте `dry_run = true` →
Run. У логах буде видно, що б бот опублікував, але в канал нічого не піде.

Потім — `dry_run = false` (або просто запустіть workflow вручну повторно).

## 4. Як змінити канал

1. Створіть канал (або візьміть наявний) і додайте туди бота адміністратором.
2. Дізнайтеся ID нового каналу (розділ 3.3).
3. **Settings → Secrets → `TELEGRAM_CHANNEL_ID`** → Update → вставте новий ID.
4. Перевірте: Actions → **Run workflow** з `dry_run = true`, потім без нього.
5. Старий канал бот більше не чіпатиме.

Якщо канал **приватний** (без публічного username), усе працює, але сторож не
зможе перевіряти «останній пост» через `t.me/s/` — він покаже `SKIP` для каналу
й перевірятиме лише прогони.

## 5. Як перевірити, що публікація жива

### Спосіб 1 — канал (5 секунд)

Відкрийте канал. Якщо останній пост старший за добу — щось не так.

### Спосіб 2 — GitHub Actions

https://github.com/enterpriseimpossible-sudo/wronki-news-bot/actions

- **Wronki news bot** — останній прогін має бути зеленим і молодшим за ~10 хв.
- **Wronki watchdog** — після пушу (розділ 12) має бути зеленим, запуск кожні 30 хв.
  До пушу його роль виконує `monitor.py` (спосіб 3).

### Спосіб 3 — локально (найточніше)

```powershell
cd F:\ER7\Wronki-News-Bot
.\.venv\Scripts\python.exe monitor.py
```

Приклад здорового результату:

```
Wronki watchdog  2026-10-24T09:00:00Z
  OK    GitHub Actions   №7100 завершився 12 хв тому (ліміт 3 год)
  OK    Самоланцюжок     №7101 зараз in_progress
```

Коди виходу: `0` — все добре, `1` — тиша (потрібен ремонт), `2` — сама перевірка

--max-chain-gap-minutes 30`. «Самоланцюжок» = FAIL, якщо за 30 хв не було прогону з
`workflow_dispatch` — навіть коли останній прогін зелений (випадок 20.10.2026) або
бота тримає лише `schedule`.

Додайте секрет `WRONKI_ALERT_CHAT_ID` (ваш особистий chat_id; дізнатися можна
через @userinfobot). Тоді при тиші прийде повідомлення. `monitor.py` **ніколи**
не надсилає алерт у сам канал — це перевіряється тестом.

## 7. Локальна панель (необов'язково)

```powershell
$env:GH_TOKEN = "..."     # токен із правом Actions: read and write
.\panel.bat               # http://127.0.0.1:8765
```

Панель уміє: редагувати `config.json` і пушити його в репозиторій, змінювати
розклад, запускати хмарний прогін, робити локальний тест.

Звідки панель бере токен (перше, що знайде):

1. змінна `GH_TOKEN` або `GITHUB_TOKEN`;
2. файл за шляхом `GH_TOKEN_FILE`;
3. `gh auth token` (якщо стоїть GitHub CLI);
4. `%LOCALAPPDATA%\gh\token.txt` (старий спосіб).

Перевірити, що знайдено: `http://127.0.0.1:8765/api/health` (токен там **не**
показується, лише джерело).

## 8. Зміна джерел, радіуса, розкладу

Усе — у `config.json`:

| Поле | Що означає |
|---|---|
| `radius_km` | радіус від центру (30 км) |
| `max_age_hours` | публікувати лише новини не старші за N годин (1) |
| `max_items` | максимум новин за один прогін (5) |
| `translate` | переклад PL→UA |
| `instant` / `poll_minutes` | розклад: `instant=true` → кожні `poll_minutes` (мін. 5) |
| `sources[]` | джерела: `name`, `url`, `type` (`rss`/`html`/`tg`), `lat`, `lon`, `enabled` |

Зміни в `config.json` **не діють, поки файл не потрапить у `main`**. Або через
панель (вона пушить сама), или `git commit` + `git push`.

## 9. Діагностика

| Симптом | Причина | Що робити |
|---|---|---|
| Прогін червоний, у логах `401 Unauthorized` / `Bad credentials` | `GH_PAT` прострочений або відкликаний | Випустити новий PAT, оновити секрет |
| Прогін червоний, `403 Forbidden` | у PAT немає `Actions: write`, або Actions вимкнено | Перевірити scope PAT / Settings → Actions |
| Прогін зелений, але постів немає годинами | джерела не дали свіжих новин або `max_age_hours` замалий | `python monitor.py`, потім `DRY_RUN=1 python bot.py` |
| У каналі дублікати | загубився `state.json` (кеш GitHub живе 7 днів) | нічого не робити; наступні прогони знову наповнять стан |
| `Жодне з N увімкнених джерел не дало новин` | блокування джерел / змінився HTML | перевірити доступність джерел, оновити парсер |
| Панель: «Не вдалося запустити хмарний прогін» | немає токена або він без прав `Actions: write` | `GET /api/health`, задати `GH_TOKEN` |
| Сторож червоний, `RESULT: FAIL` | канал мовчить довше за поріг | дивитись лог `wronki.yml`, перевірити `GH_PAT` |

Логи: Actions → потрібний прогін → job `run` → крок `Run bot`. Секрети в логах
не друкуються.

## 10. Обмеження (чесно)

- **`schedule` у GitHub — best-effort.** Може затриматись на кілька хвилин, а в
  рідкісних випадках не спрацювати. У локальному `wronki.yml` він є (`*/10`), у
  GitHub з'явиться після пушу (розділ 12).
- **Розклад може вимкнутись після 60 днів без активності в репозиторії.**
  Достатньо будь-якого коміту раз на два місяці.
- **`state.json` живе в кеші GitHub 7 днів.** Якщо бот простоює довше, історія
  дедуплікації губиться (старі новини не повторяться через `max_age_hours`).
- **Токен PAT треба ротувати** до закінчення терміну — інакше самоланцюжок
  помре (тепер — червоним кроком); після пушу його піднімуть `schedule` і сторож,
  але тільки з новим токеном.
- **Панель без пароля**, слухає лише `127.0.0.1`. Не відкривайте її в інтернет.
- **Парсери HTML крихкі**: змінився сайт — джерело може тихо давати 0 новин.

### План Б, якщо самоланцюжок не спрацьовує

20.10.2026 сервіс уже зупинявся саме так. Варіанти за зростанням складності:

1. **Самоланцюжок** — основний шлях; працює, поки живий `GH_PAT`.
2. **Зовнішній cron** (cron-job.org, UptimeRobot) — раз на 5 хв робить `POST` на
   `https://api.github.com/repos/enterpriseimpossible-sudo/wronki-news-bot/actions/workflows/wronki.yml/dispatches`
   з тілом `{"ref":"main"}` і заголовком `Authorization: Bearer <той самий PAT>`.
   Дублікатів не буде: зайвий прогін побачить активний і не стане плодити новий.
3. **Власний сервер** — `deploy/install.sh` (systemd timer кожні 5 хв). Тоді
   самоланцюжок краще вимкнути, щоб не було двох джерел.
